# @keploy/playwright

Joins a Playwright suite to keploy's Universal Mocker. `keploy mock record` records the calls each test's browser and app server make; `keploy mock replay` answers them from the recording, so the suite runs without its backends. keploy judges every recorded test, and lists each test it cannot replay with a reason.

This package tells keploy where each test begins and ends. Through it, keploy skips a test it set aside and fails a test whose calls changed. It speaks keploy's scope protocol v1, the same one go-sdk's `keploytest` speaks, and decides nothing itself.

## Use

```sh
npm install --save-dev @keploy/playwright
```

It needs Node.js 20 or later. Its rows run on Node.js 20, 22 and 24.

Import `test` and `expect` from this package instead of `@playwright/test`. A fixture file that extends `test` extends this one:

```ts
import { test, expect } from '@keploy/playwright';

test('lists the apps', async ({ page }) => {
  await page.goto('/apps');
  await expect(page.getByRole('row')).toHaveCount(3);
});
```

Run the suite under keploy with `KEPLOY_PROVEN=1`, one worker and no retries:

```sh
KEPLOY_PROVEN=1 keploy mock record -c "npx playwright test --workers=1 --retries=0"
KEPLOY_PROVEN=1 keploy mock replay -c "npx playwright test --workers=1 --retries=0"
```

`KEPLOY_PROVEN=1` is keploy's switch for its proven model. keploy speaks this package's wire, scope protocol v1 (the claim, begin, end, given and refusal), only under it. Without it, keploy answers the worker's claim with a plain 404, and every test of the worker fails with `keploy: this keploy agent answered 404 to POST /agent/instance, so this worker cannot claim keploy's run: ...`, which names the switch. A begin, an end or a refusal answered with a plain 404 names the switch the same way.

keploy's first release runs one test process at a time. A second worker that is still alive while another runs is refused by keploy, and its tests fail. Turn retries off: keploy sets aside a test it cannot prove, with its reason, and fails a test whose calls changed, and a retry changes neither. keploy runs each test once in a run, so a test Playwright runs again (a retry, from `--retries`, the config or `test.describe.configure`, or a repeat of `--repeat-each`) fails without beginning, saying why, and keploy is told (`POST /agent/refusal`), so its verdict on the run names the test.

## Without keploy

With `KEPLOY_MOCK_AGENT` unset or `off`, nothing changes. Only `keploy mock record` and `keploy mock replay` set that variable.

## Under keploy

- **Claim.** Each worker claims keploy's run before its first hook or test (`POST /agent/instance`). The claim uses the worker's Playwright project name as its key, or `.` for an unnamed project, and names the project directory keploy names (`KEPLOY_MOCK_PROJECT`) as the folder of its tests, the folder the test files are named from (the current directory only when keploy names none). So a suite run from a folder above its keploy project, such as `cd .. && npx playwright test` in `mock.command`, is filed under its project. A worker that Playwright starts again after a failed test claims again. Calls that `beforeAll`/`afterAll` hooks and worker fixtures make outside every test are answered from the worker's claim, one slice per Playwright project. The `beforeAll` and `afterAll` hooks of a describe group whose tests keploy has all set aside still run, and their calls are answered from the claim: each test is skipped at its begin, after the group's hooks have started.
- **Begin.** Each test begins (`POST /agent/scope/begin`) before its `beforeEach` hooks. keploy builds the test's ID as `[project::]file::titles`. The file is relative to the project directory keploy names (`KEPLOY_MOCK_PROJECT`). The titles are the describe groups and the test's own title, joined with ` › `.
- **Skip.** When keploy has set a test aside, the test is skipped through Playwright's own skip, and the report shows keploy's reason (`keploy: ...`). The test's output shows it too (`keploy: ... (keploy skipped <titles>)`), since Playwright's list, line and dot reporters print a test's output but not its skip's reason.
- **Settle.** Before the test's `context` (and its `page`) closes, the test waits until none of its pages' calls is in flight. A context the test makes itself (`browser.newContext()`) is the test's own to close. Calls are counted by the browser's own request events, and no time window decides. A call that never ends keeps the test waiting until Playwright's test timeout fails it. The test shows a step that names each call still in flight. A call is not waited for once the browser has cancelled it, which happens when its page loads another document, its frame is removed, its page closes or the test closes its own context. Nor once a route of the test's own has answered it (its `route.fulfill` returned): the call has the route's whole answer, though the browser may report no end for it (Chromium for a Web Worker's script a route answers with a redirect, whose worker never starts, with no keploy too; Firefox for the first request of a redirect a route answers). Nor once the route's handler has thrown while the route still holds the call (WebKit refuses a redirect, and Playwright's `fulfill` throws its own error), as Playwright then sends it nowhere. A handler that returns and leaves its route holding the call might still send it on, so the call is waited for as any other. Settle reads this from Playwright's own route handling, past its API; with a Playwright that has none, such a call is waited for as any other. When a frame loads another document, the calls it drops are those the browser reported before the new document's answer: a call the new document makes as it loads (a script or an image its parser asks for) is waited for, even when the browser reports it before the frame's commit, as Firefox can. Nor are the calls a page's frames had in flight when the page loaded another document: the frames go with the old document, and Playwright reports no end for their calls, ordinary or keepalive (`navigator.sendBeacon`, `fetch` with `keepalive`, the telemetry a payment form's frame sends, which the browser goes on sending), nor for a frame's own document request still loading, so waiting for them would hold the test until its timeout. The browser goes on sending a keepalive call only while the test's context lives: one still in flight when the test ends is cut by the context close, so its answer may not be recorded. A closing page cancels only its own calls: a popup that closes cancels nothing of its opener's. A route change inside the page (the history API) cancels nothing, even after an answered call. A service worker's calls are counted too. No page's change drops them, but the test closing its own context does, as it ends the worker. A Shared Worker's are not: Playwright reports none of a Shared Worker's calls in any engine, and Chromium reports no end for its script. So in every keploy test, seeded or not, the page's `SharedWorker` starts each worker as the app asked and tells the test its script's URL, and settle does not wait on a request of that frame at that URL. The test says so once for each Shared Worker script, naming it and the next step: have the test wait for what the worker does (a message it posts, or what the page shows from it) before it ends, as a call the worker still has in flight then is cut there.
- **End.** The test ends (`POST /agent/scope/end`) after its last teardown, with its own outcome. When keploy saw a call with no recorded answer, or a recorded call the test no longer made, the test fails with keploy's text.
- **Given values.** `await given(name, value)` tells keploy a value the test made itself. Examples are a session token it signs and a name it stamps with the time. keploy then follows the value wherever the test's calls carry it, as it follows an incoming request's values in a server test. Give a distinctive value, whole, as the calls carry it. `given` must be called inside a test, or in its `beforeEach` or `afterEach` hooks. It returns the value. It needs a keploy whose agent serves `POST /agent/scope/given` (see "What the run says when ..." below).

- **Seeded random numbers.** Each test's browser draws its random numbers (`Math.random`, `crypto.getRandomValues`, `crypto.randomUUID`) from a seeded stream, so a replay draws the numbers its recording drew. A page that picks what to load at random (an A/B coin, such as stripe.js's at each page load) then makes the same calls in replay as in its recording, which keploy can answer.
  - **Where the seed comes from.** Each test's begin sends a seed drawn afresh (`seed`, 128 bits as hex). keploy answers the seed to draw from. A record answers the begin's own, and keeps it in the test's mapping entry (`seed:`, beside its `at:`). A replay (and keploy's auto-replay) answers the one the recording kept. So two tests draw different numbers, and recording a test again draws new ones: an ID the browser makes is not sent twice to a real server. The seed is not derived from the test's name, so a test whose entry is renamed keeps its seed with the rest of the entry.
  - **The test process.** The Node worker that runs the test draws `Math.random` from the same seed, from its own stream, from the test's begin to its end: its `beforeEach` and `afterEach` hooks and its fixtures included. So data a suite makes in the test process (a lead named `Lead ${Math.random().toString(36).slice(2, 7)}`) is in replay the data its recording made, and a mocked dependency's answer still matches the test's own assertion. At the test's end the worker's own `Math.random` is back, unless the test put its own stub there, which it keeps.
  - **faker in the test process.** Where a test file can import `@faker-js/faker` (8, 9 or 10), the instances the package makes as it loads (`faker`, `fakerDE` and the other locales, `simpleFaker`) draw from the test's seed too, each from its own stream, so the names, emails and IDs a test makes with them are in replay the ones its recording made. keploy takes them from the module the test file's own import loads: faker 10 is one module for CommonJS and ES module test files alike, and for faker 9 an ES module test file's instances are its ES module copy's. A test that seeds an instance itself (`faker.seed(n)`) draws that instance as it seeded it, and at the test's end each instance draws its own again, its own generator not moved by the test's draws. Where faker is installed but keploy cannot load it (an ES module on a Node older than 20.19 or 22.12), the worker prints `keploy: @faker-js/faker is installed where the tests import it, but keploy cannot seed it (<why>), ...` once, with the next step.
    - A draw made while a stack trace is prepared is the worker's own, not the test's. Playwright maps stack frames through source maps, and the first time a test's stack reaches a file (a helper or page-object file's `test.step`, an `expect`, a read of an Error's stack), it parses that file's map with a sort that draws `Math.random`. A worker parses each file once, in whichever test reaches it first. So those draws do not depend on which tests its worker ran before it.
    - To tell those draws apart, every stack trace is prepared through a wrapper while a test is seeded: `Error.prepareStackTrace` reads back a wrapper of the function last set there (the same one on each read), and setting that wrapper sets its function. At the test's end `Error.prepareStackTrace` is again a plain property holding the function last set, unless the test defined that property itself, which it keeps.
    - A worker fixture registered with this package's `test.extend` or `test.use` draws the worker's own `Math.random` while it is set up, until it calls `use()` (or fails before). Playwright sets a worker fixture up in the first test that asks for it, after that test's seeding began, unless it is `auto`. Its draws (a test account made once for the worker's tests) would otherwise come from that test's stream and shift the test's own. A test fixture is the test's, and draws from its stream. Anything else that draws while a worker fixture is set up (a timer or an event handler of the test's) draws the worker's own too.
    - With both, a test draws the same numbers whichever tests its worker ran before it: replayed alone, after keploy set an earlier test aside, or in a new worker after a test failed. "What the run says when ..." (below) names what a worker does once, in whichever test first needs it, that neither covers.
  - **Your own faker instances.** An instance the suite makes itself as a test file loads (`new Faker(...)`, `new SimpleFaker(...)`) seeds its own generator from the worker's `Math.random` then, so it draws other numbers each run. Give it to `seedFaker` and it is seeded as the prebuilt ones are, from its own stream of each test's seed:

    ```ts
    import { Faker, de, en } from '@faker-js/faker';
    import { seedFaker, test } from '@keploy/playwright';

    const fakerMine = seedFaker(new Faker({ locale: [de, en] }), 'mine');
    ```

    The name names the instance's stream, so give each instance its own: two given one name make the same data. An instance given as a file loads, in `beforeAll` or while a worker fixture is set up is seeded in every test after; one given in a test (its `beforeEach`, its body, a test fixture) until that test's end. One the suite makes inside a test needs no call: it seeds its generator from the test's seeded `Math.random`. The worker's seeded line names `seedFaker` for these instances, and `seedFaker` throws, naming the next step, when it is given no faker instance it can seed or no name.
  - **A recording that kept no seed** (made before keploy kept seeds, or with seeding off), a test pulled from a Keploy branch (the branch keeps no seed), or a keploy from before seeds, answers none. That test's browser and test process then draw their own numbers, and the test prints `keploy: keploy answered the begin of <test> with no seed, so its browser and its test process draw their own random numbers: ...`. A recording made before seeds or with seeding off is seeded by recording it again with seeding on.
  - **What is seeded.** The seed is installed before any script of the page runs, in every frame of the test's `context`, cross-site frames included. Each function has its own stream, and each document its own. A document is named by its page, by its path (not its host, port or query, which a replay may change), and by how many documents of that path loaded before it: in its frame, for a frame of its parent document's origin; else in its origin in the tab. So a reload draws new numbers, the same ones each run, and two tabs of one test at one path draw different ones: an ID the browser makes for each tab (a tab or client ID, an idempotency key) stays its own, in the record as in the app. Only the test browser changes: not the app or its server.
  - **Workers.** A Web Worker a page starts (`new Worker(url)`, classic or `type: 'module'`) draws from its own streams too, named by the document that started it, its script's path and how many workers that document started at that path before it, so it draws the same numbers at replay. In WebKit, a Web Worker that a seeded Web Worker starts (classic or module, and the ones that one starts in turn) is seeded so too, named by the worker that started it, its script's path and how many workers that worker started at that path before it. Chromium's and Firefox's routes reach no script of a worker that a worker starts, so there it starts as the app asked, with no mark, and draws the browser's own numbers. One a seeded worker starts from a `blob:` or `data:` URL, or from a URL the browser refuses with the mark, does too. Each says so (below), once for each address: the worker that started it posts its address to keploy's route, which answers it, so neither a route of the test's nor the app's server sees that request. A worker that a worker named below starts draws the browser's own numbers too, and that worker's line says so. A Shared Worker, which a test's pages share, is named by its script's path, its name and how many times the test started it. keploy reaches a worker's script through the test's browser context: the page's `Worker` and `SharedWorker` add a `__keploy_worker` mark to the script URL's query, and a route of the context answers that request, asking the app's server for the script with no mark. A Web Worker's answer is the app's script itself, the bytes its server sent, never read and written again (so a script served in another charset, which Chromium reads a worker's script by, reads as with seeding off; a byte order mark and a hashbang line stay first), with the worker's seeding ahead of it on its first line, loaded from a URL keploy marks and answers itself (`importScripts` for a classic worker; an `import` ahead of the app's imports for a module worker, so the seeding runs before the modules the app imports), and a `//# sourceURL` of the app's URL at its end unless the app names one: the worker loads the app's script once. When the script's response carries a Content-Security-Policy that could refuse that load (one keploy cannot tell allows a script from the worker's own origin: its source list for scripts (`script-src-elem`, else `script-src`, else `default-src`) lists `'self'`, `'strict-dynamic'`, `*`, the origin's scheme or the origin itself (its scheme, host and port, or a wildcard host that holds it, with a path that holds the script's, or none), and for a module worker so does its list for workers (`worker-src`, else `child-src`, else those); it has no `sandbox`; a classic worker's requires no Trusted Types for scripts; and it upgrades no http request (`upgrade-insecure-requests`), which Chromium never does for a loopback host (`localhost`, `127.0.0.1`), so helmet's default policy allows it there in Chromium, and in Firefox and WebKit on https), the seeding itself is on the app's first line instead, which no policy refuses; in a module worker it then runs after the modules the app's script imports, and the test says so (below). A classic worker's answer starts with a `"use strict";` of keploy's when the app's script has `'use strict'` in its directive prologue, so the app's code stays strict. A Shared Worker's answer is the worker's seeding, which then loads the app's own script from the URL the app asked for, with no mark; where the script's policy could refuse that load (as above), it is the app's script itself, as a Web Worker's is, with the seeding on its first line, run at the worker's marked URL, in a module Shared Worker after the modules the app's script imports, which the test says (below). Only the browser's load of a worker's script is answered so: a request the worker's own code makes at its script's URL (`fetch('')`, a fragment alone, an `XMLHttpRequest` of `''`, which resolve against the marked URL) goes on to the app's server with the mark taken off and gets what the server answers. A seeded worker's `fetch` and `Request` take the mark off too: a fetch or a `Request` at the script's own URL asks for it with no mark, and a fetch whose referrer the browser would pick (the init names none, and a `Request` it is given was made with no referrer and the default policy) sends the script's URL with no mark as its `Referer`. JavaScript cannot set the rest, so the app's server sees the mark in these, the same at record and replay (the mark comes from the test's seed and the worker's place): the `Referer` of a worker's `XMLHttpRequest` and `importScripts`, of a fetch of a `Request` made with a `referrerPolicy` of its own and no referrer, and, in Chromium and WebKit, whose route reaches nothing a Shared Worker asks for after its script, of a Shared Worker's load of its own script (keploy's answer loads it so); in Chromium and WebKit, the URL of a Shared Worker's `XMLHttpRequest` of its script's own URL; and, for a worker that runs at its marked URL with no seeding (one whose script a route of the test's own answers itself, or a Shared Worker it sends on with options of its own, below), the `Referer` of each of its requests and, in Chromium and WebKit, the URL of a Shared Worker's `fetch('')`. So the app's script runs at its own URL: a stack trace through it names the app's URL with no mark (in Firefox, whose stacks go on through the code that queued what runs, a worker's `Error` and `DOMException` stacks leave keploy's frames out), the `filename` of an error event, in the worker and in the page, shows none, and the worker's `location` shows none. A module Web Worker's `import.meta.url` is its marked URL: one load cannot both run keploy's seeding first and give the module the app's URL. The URLs its imports resolve against are the app's, as the mark is in the query, which a relative specifier other than a fragment alone replaces. A Shared Worker's `import.meta.url` shows no mark, but in a module one whose seeding is on its script's first line (above), where it is its marked URL. The app's line numbers are kept; keploy's seeding shifts the columns of the app's first line. An error the browser's own call throws in a seeded function or in the worker's `location` (a float array to `getRandomValues`, a `this` that is no `Crypto`) shows none of keploy's frames on its stack either, but in a worker whose seeding is on the app's first line (a policy that could refuse keploy's load, above): there its frames show at the app's URL, on that line. keploy wraps the page's `Worker`, its `terminate` and `SharedWorker` in every test, seeding off too, so their `toString()` shows keploy's code where it would show the browser's native code. keploy's answer has the status and headers the app's server gives the script (a worker's policy comes from them). The test's routes and the app's server see a Web Worker's script loaded once, as with seeding off, under any referrer policy of the script's or of the document that started it (a script the server redirects aside, below); the seeding's own load reaches neither. Chromium and WebKit route nothing a Shared Worker loads after its script, so the app's server is asked for a Shared Worker's script twice: by keploy, and by the worker (once, by keploy, for one whose seeding is on its script's first line). Chromium and WebKit let the route reach none of what a Shared Worker loads after its script, so a module Shared Worker imports its seeding as a `data:` module ahead of the app's script; where its script is served with a Content-Security-Policy that refuses `data:` scripts, keploy's answer runs the seeding itself and then imports the app's script, and the connections that came before that script ran reach its `connect` handlers after, in order, as events keploy dispatches (their `isTrusted` is false). The test's end never waits on a Shared Worker's script, whichever route answers it. So a seeded test's requests go through keploy's routes, and while a context has a route (any `context.route`), the browser asks the server for each request rather than answering it from its cache, in every engine. That holds at record and at replay alike, so a replay asks the app's server for what its recording asked: measured on one test's steps (a page, a second page on the same stylesheet, script and image, a reload, the first page again), the server got 20 calls in Chromium 158 and WebKit 27.2 (11 with no route) and 24 in Firefox 159 (12 with no route), the same ones at record and at replay in each engine. keploy's route stays ahead of every route the test adds to its context or its pages (with `route` or `routeFromHAR`, and through `unroute` and `unrouteAll`), so no route of the test's sees the mark: a worker's script load reaches the test's routes at the URL the app asked for (`**/worker.js` matches it). When the test's `unroute` or `unrouteAll` takes the last route of its own off a page, Playwright sends each request a route it took off still held on, as the browser asked for it, so that route's `continue`, `fulfill` or `abort` then fails with Playwright's own error (`route.continue: Route is already handled!`, dropped after `unrouteAll({ behavior: 'ignoreErrors' })`) and its `fallback` goes on to the next route. keploy's route stays, so keploy does the same before the `unroute` or `unrouteAll` returns: it answers each worker script load such a route held, seeded, asking the app's server for the script once, and sends any other request on; the route's call after that fails with the same error, seeding on or off, and the app's server never gets the mark. The same holds for the context's last route, for a request from a page with no route of the test's. `unrouteAll` takes off the test's routes alone, with the behavior the test gives, and keeps keploy's: with `'wait'` it waits for the test's routes, as Playwright does, so a route that then continues a worker's script load has keploy answer it as above. A route that continues it (a catch-all `route.continue()`) or falls back leaves it to keploy, which answers it as above, asking the app's server for the script with what that route asked: the URL, method, headers or post data it gave `continue` or `fallback` (a header the server needs, a stand-in's URL). A Web Worker runs the script that answer got, so a route that answers once (`times: 1`), counts its loads, or picks the worker's script by its destination (`sec-fetch-dest: worker`) sees what it sees with seeding off. Chromium and WebKit route nothing a Shared Worker loads after its script, so a Shared Worker whose script such a route sends on otherwise than the browser asked (headers other than the browser's, a URL other than the one the app asked for, another method, or post data; of two routes, what the last one asks) gets the answer to what that route asked, whole: it runs unseeded, at its marked URL. One sent on with the browser's own headers, or with no options, is seeded. One that aborts it aborts it; one that answers it itself (`route.fulfill`) answers it so, and that worker runs the test's script unseeded, at its marked URL. A request event is not a route: a `waitForRequest` or `page.on('request')` of the test's own sees a worker's script request with the mark. These say so as the test runs, once each, naming the worker and the next step: a worker started from a `blob:` or `data:` URL, or from a URL the browser refuses with the mark (a Trusted Types policy), in Chromium and Firefox a worker that a worker started, a worker whose script a route of the test's own answered itself, a Shared Worker whose script such a route sent on with options of its own, and in Firefox a Shared Worker, whose script Firefox's route does not reach. A Service Worker draws the browser's own numbers: keploy cannot put its seeding ahead of its script. Each one the browser registers says so in the test that registered it, once for each script address, naming the next step: if the tests do not need it, set `serviceWorkers: 'block'` in the project's `use`, so Playwright registers none and nothing is said. A worker whose script a Service Worker may answer would show that Service Worker keploy's mark, so it starts as the app asked, unseeded, and says so once for each address, naming the Service Worker and the same next step: a Web Worker of a page a Service Worker controls, and a Shared Worker of a page a Service Worker controls or whose URL the scope of a registration keploy knows of holds. keploy marks a Shared Worker only when it knows that no registration's scope holds its URL: each page asks the browser for its origin's registrations as it begins, and the pages of the test's context tell each other, on a `BroadcastChannel` of keploy's, the scope of each registration they find and of each `register` they call (before the browser registers it). Each `register` holds a Web Lock of keploy's (`keploy-sw-register`, which `navigator.locks.query()` shows) from before the browser registers it until it settles, and a page asks for its registrations only once the browser has said that no page holds that lock, so a page that begins while another is registering one is not told. A Shared Worker a page starts before the browser has answered (a script that runs as the page loads may), in a page that began while another page of its origin was registering a Service Worker, or in a page that cannot read its Service Workers or its Web Locks (a sandboxed one), starts as the app asked, unseeded, and says so with the same next step: with `serviceWorkers: 'block'`, keploy knows at once that no Service Worker can answer, and seeds it. The worker still takes its place at its path, so the next worker there draws what it drew at record.
  - **How a page is named.** By its place in the test's own order, the same in every run:
    - a page the test opens (`context.newPage()`, the `page` fixture's among them), by the order in which the test asked for its pages, even when it asks for two at once, in each of its documents: its first one (the `about:blank` it has before its first `goto`, which `page.setContent` writes into) too;
    - a popup a page opens with `window.open`, at the opener's origin, as the window that the opener's document opened first, second, and so on (two popups opened at one moment keep their places);
    - a frame of its parent document's origin, by that document and by its place among the document's frames: the path its element asks for (`src`, or `about:srcdoc`, or `about:blank` for none) and how many frames the document had put in at that path before it, counted in the order the document holds the frame elements when it numbers them (as the task that put them in ends, or as a frame's document begins), never by their windows (the document finds a frame by its `frameElement`). For frames one task puts in out of document order, that is document order in Chromium and WebKit and the order they were put in in Firefox: the same each run, for a given app and engine. Frames at other paths, and the order the frames' documents load in, do not move it; it keeps its place whatever it loads, and one put in after a frame's removal takes the next number at its path. A frame in an open shadow root is placed so too. An `about:blank` frame does not draw its parent document's numbers;
    - a frame under a parent of another origin, which it cannot read (a cross-site frame), by the page it is in and its path. One with no session storage to count its documents in (a sandboxed frame without `allow-same-origin`) is never seeded (below).

    A document the seeding cannot place draws the browser's own numbers, never another page's. The test then prints `keploy: in <test>, the document at <address> drew the browser's own random numbers, so its draws may differ at replay: ...` with the reason, once for each address and reason, in its record and in each replay. The address is the document's origin and path; for an opaque origin (`about:blank`, `about:srcdoc`, a `data:` URL, a sandboxed frame or page) it is the document's URL with no query or fragment, and `about:blank` for a window's first document that has no URL yet (Firefox runs init scripts there before it has one). "What the run says when ..." (below) lists those documents.
  - **What keploy is told.** The begin says what the test means to do (`random: "seeded"` or `"own"`). The end says what its pages drew from: `"seeded"` when a page opened in its seeded `context`, `"own"` when a page opened there unseeded, or when keploy answered no seed. When a test's calls still vary between runs, keploy can then say whether its pages were seeded, so the variation comes from somewhere the seeding does not reach, or whether seeding them is left to try.
  - **When a replay draws otherwise.** A seed gives a replay its recording's numbers only while each stream is drawn the same number of times, in the same order. So a seeded test's end also sends keploy a note (`note`, JSON of at most 16 KiB) of how many times the test process drew each of its streams (`Math.random` and each seeded faker instance), how many times each placed document drew each function, and how many frames each document put in at each path. A record keeps the note with the test's recording, and keploy never reads it. A replay's begin is answered the recorded note, and the replay's end prints one line for each difference, with its next step:
    - `keploy: <test> drew Math.random 2 times in the test process at this replay and once in its recording, so ...`: register worker fixtures with this package's `test.extend`, use a library that draws on its first use once outside the tests, and draw a fixed number of times;
    - `keploy: <test>: the document at <address> drew crypto.randomUUID 3 times at this replay and 2 times in its recording, so ...`: draw a fixed number of times, and give each frame its own path;
    - `keploy: <test>: the document at <address> put in 2 frame(s) at /chat at this replay and 1 in its recording, so ...`: give each frame at that path its own `src` path, or put them in in a fixed order and number.

    A test prints at most 8 such lines, then one that says how many more differences it found. A note that would be over 16 KiB keeps the documents that reported first and counts the rest as cut; a document one of the two notes cut is compared with nothing. A seeded replay that keploy answers with no note says so once per worker: its recording keeps none (recorded with keploy v3.7.5 or older, or with @keploy/playwright 0.1.1 or older), or this keploy keeps none (v3.7.5 or older). Record the tests again with a keploy that keeps notes.
  - **On by default.** To turn it off, for record and replay alike:
    - for the whole run: `KEPLOY_SEED_RANDOM=off` (or `0`, `false`; unset, `on`, `1` or `true` seed; any other value fails every test, naming the variable);
    - for a project, a file or a test: the option `keploySeedRandom: false`, in the config's or a project's `use`, or with `test.use({ keploySeedRandom: false })`. Its type is `KeployOptions`: `defineConfig<KeployOptions>({ use: { keploySeedRandom: false } })`.

    The cost, which the first such test of a worker prints: the test process and the browser draw their own numbers each run, so data a test makes from them differs from its recording's while a mocked dependency answers with the recording's. A test that checks one against the other fails, or keploy sets it aside, and a page's random choice may make calls the recording never saw.

Any answer from the agent that this package cannot trust fails the test. That covers an agent it cannot reach, an error answer, an unreadable answer, and an answer that does not speak scope protocol v1. Nothing is retried.

## What the run says when ...

keploy seeds, places and waits for what it can reach in the test browser and the test process. What it cannot reach, the run names as it happens, with the next step, as each case below says. Each line starts with `keploy:`.

- **... keploy's agent is missing, too old or answers wrongly.** Any answer from the agent that this package cannot trust fails the test (above). A keploy too old for one feature fails or names only that feature:
  - `given` needs the agent route `POST /agent/scope/given` (keploy/keploy#5016): keploy v3.6.192 and later serve it; with the enterprise keploy, that is an enterprise release on keploy v3.6.192 or later. An older keploy answers that route with a plain 404, and `given` fails the test with `keploy: this keploy agent answered 404 to POST /agent/scope/given, so it cannot take the given value <name>: given needs keploy v3.6.192 or later (keploy/keploy#5016), or an enterprise release on keploy v3.6.192 or later; an older keploy answers 404 there`. Claim, begin, settle and end do not need that route.
  - Seeds need a keploy that keeps them: keploy v3.6.217 (keploy/keploy#5121) and later; with the enterprise keploy, an enterprise release on keploy v3.6.217 or later. An older keploy reads no seed from a begin and answers none, so each test's browser and test process draw their own random numbers, and each test says so (`keploy: keploy answered the begin of <test> with no seed, ...`, above). Claim, begin, settle and end work with it as before.
  - A replay's lines on how it draws need a keploy that keeps each test's note; a seeded replay that keploy answers with no note says so once per worker (above).
- **... a call does not end.** Settle shows a step that names each call still in flight, and a call that never ends fails the test at Playwright's test timeout, named there. Settle drops a call only when the browser cancels it, the document that made it is gone, or a route of the test's has answered it or holds it after its handler threw (above), so it fails toward waiting, never toward a cut call. A call the old document starts after the new document's answer, as it unloads (a `pagehide` or `unload` handler's), is waited for too, since settle cannot tell it from a call of the new document; it is named the same way if the browser never reports its end. A Web Worker a page terminates (`worker.terminate()`) while its script still loads: Chromium reports no end for that load, ever, so the page's `Worker` tells settle which of its document's workers at that URL it terminated (each document numbers its Web Workers at a URL in the order it starts them), and settle stops waiting on that worker's load; Firefox and WebKit go on loading the script and report its end, which settle waits for. On a seeded test, keploy's route fetches a Web Worker's script, and its load ends when keploy's answer has gone to the browser or the browser has dropped it.
- **... in Chromium, a page loads a script at the URL of a Web Worker it terminates.** Settle finds a terminated Web Worker's script load by its place among the script requests its document's frame reported at that URL: the k-th Web Worker the document started there is taken to be the k-th such request. A page's own script, or a worker's `importScripts`, at that URL in that document takes a place too, so settle may stop waiting on that script's load while it is in flight (the test can end before it does) and, with seeding off, go on waiting on the terminated worker's load, which Chromium never ends, until Playwright's test timeout fails the test, naming that load as a call that did not end. Playwright shows a Web Worker's script load as a script request of the page's frame, as it shows the page's own, so settle cannot tell them apart. Next step: serve the worker's script at a URL no other script of the page loads.
- **... a module Web Worker reads its `import.meta.url`.** On a seeded test it is the worker's marked URL, the app's URL with keploy's `__keploy_worker` mark added to its query: keploy answers that one load with its seeding ahead of the app's module, so the module runs at the URL the browser loaded it from. The path is the app's, so a URL the module builds from `import.meta.url` with a relative path (`new URL('./data.json', import.meta.url)`), or with a query of its own, is the app's URL with no mark, and so are the URLs its imports resolve to. Only code that reads or compares the exact URL, or adds a fragment alone to it, sees the mark; the mark comes from the test's seed and the worker's place, so it is the same at record and at replay. A module Shared Worker whose seeding is on its script's first line (below) reads its marked URL so too. With seeding off, or for a classic Web Worker (its `location`) or another Shared Worker (its `import.meta.url` too), the worker sees the app's URL.
- **... a module worker's script is served with a Content-Security-Policy that could refuse keploy's load.** When keploy cannot tell that the policy allows a script from the worker's own origin (`'self'` in `script-src` or `default-src` does; the rest under Workers, above), keploy puts the worker's seeding on its script's first line, and in a module that line runs after the modules the script imports: a random number one of those modules draws as it loads is the browser's own, so it may differ at replay. This holds for a module Web Worker and, in Chromium and WebKit, a module Shared Worker. The test says so once for each address (`keploy: in <test>, the module Web Worker at <address> is served with a Content-Security-Policy that could refuse keploy's load of a script from the worker's own origin, ...`, or `module Shared Worker`), with the next step: if one of those modules draws as it loads, have the policy allow scripts from the worker's own origin (`'self'` in `script-src`) where the tests run, or serve the worker's script with no Content-Security-Policy there, and keploy loads its seeding ahead of those modules. A classic worker's seeding on its first line runs before any of the app's code.
- **... a page starts a Shared Worker.** Settle does not wait for it, and the test says so once for each Shared Worker script (`keploy: in <test>, a page started the Shared Worker at <address>: keploy does not wait for its script or its calls ...`), with the next step: have the test wait for what the worker does before it ends.
- **... the browser starts a request while Playwright closes a seeded test's context.** Once the test has ended (its steps, settle and its teardown), Playwright closes its context, and keploy's route goes with it. A request the browser starts in that moment, after the test has ended, can reach the app's server with keploy's `__keploy_worker` mark in its URL, in Firefox and WebKit: a worker the test started just before it ended (its last step, or a step that then failed), whose script, or the seeding keploy's answer to that script loads, the browser asks for as the context closes. No step of the test reads what such a request gets, and nothing is said. Measured on a test whose last step starts a worker and returns, 32 runs of each with four at once: in Firefox, 9 or 10 of 32 for a Web Worker (classic, module, or one a timer starts) and none for a Shared Worker; in WebKit, 1 to 8 of 32; in Chromium, none; for a test that waits for its worker's message, none in any engine. For a test that fails by its route's error while the Web Worker it started loads: in WebKit, 2 of 76; in Firefox, none of 76. Next step: have the test wait for what the worker it starts last does before it ends (a test that fails by an error it can catch keeps it and throws it after that).
- **... a document cannot be placed.** It draws the browser's own numbers, never another page's, and the test prints `keploy: in <test>, the document at <address> drew the browser's own random numbers, so its draws may differ at replay: ...` with the reason, once for each address and reason, in its record and in each replay. Nothing tells these documents apart from the next ones at their place, so seeded, two of them could draw the same numbers:
  - a popup opened with noopener, as a link with `target="_blank"` opens one, or opened other than by `window.open` (a form, or a link with `rel="opener"`, that targets a new window);
  - a popup at another origin than its opener's page, or whose opener's page has loaded another document by the time the popup's begins, or whose opener the seeding could not place, and a frame of another origin inside one of those popups;
  - a popup that a page's first document opens with `window.open('about:blank')`, in every engine: in Chromium it has no session storage (its opener's origin is opaque), and in Firefox and WebKit its document begins before `window.open` returns, before it has a place;
  - a frame its parent document cannot list (one in a closed shadow root, or in an `object` or `embed` element), one whose document began after the frame was removed, and a frame inside one;
  - a frame under a parent of another origin that has no session storage to count its documents in (a sandboxed frame without `allow-same-origin`), alone under its parent or not, and a frame inside one: nothing tells its documents apart from the next ones at its path there (a reload, or a frame the app puts in again at its place) or from those of a frame beside it. Its line says how many other frames its parent holds, counted once the parent's parser has ended (its `DOMContentLoaded`), so frames its markup puts in after a script that holds the parser count even when this frame drew, and loaded, before they came; when the parser has not ended by the test's end, counted then; when the frame is gone by then (its parent moved on to another document), the line names no other frame;
  - a top document with no session storage that seeding can keep its count in, and a frame of its origin inside one. A document of an opaque origin has none: an `about:blank` loaded after its page's first document, a `data:` URL, or a page served with a CSP `sandbox` without `allow-same-origin`; nor has a document whose app has filled its session storage. So a test that loads `about:blank` (`page.goto('about:blank')`) and writes its page into it with `page.setContent` draws the browser's own numbers there: write into the page's first document (before its first `goto`), or serve the page from the app's origin, to seed it. A page's first document has no session storage in any engine either, but it is seeded: it is the one document of its kind in its tab (no later document there is marked, so the rule above holds for each of them), and before `newPage` returns the fixture marks it as the page's first with a value drawn afresh for each context and given only to that context's init script, so a page's own script cannot mark another document so. A frame of another origin inside such a document is placed as any frame under a parent of another origin (above);
  - a document in which a context init script of the test's own draws random numbers as the document begins: it runs before the page is named, and its line says it is in a page the test opened.

  The end still says `"seeded"` for such a test: its `context` was seeded.
- **... a worker cannot be seeded.** It starts as the app asked, with no mark, and draws the browser's own numbers, and the test prints `keploy: in <test>, the <worker, Shared Worker or Service Worker> at <address> draws the browser's own random numbers, ...` with the reason and the next step, once for each address. A worker that one of these starts draws the browser's own numbers too, and the line says so.
  - A Service Worker: keploy cannot put its seeding ahead of its script. Next step: if the tests do not need it, set `serviceWorkers: 'block'` in the project's `use`, so Playwright registers none and nothing is said.
  - A worker whose script a Service Worker may answer, since that Service Worker would see keploy's mark: a Web Worker of a page a Service Worker controls, and a Shared Worker of such a page or whose URL the scope of a registration keploy knows of holds. The line names the Service Worker and the same next step.
  - A Shared Worker started before keploy knows that no Service Worker's scope holds its URL: one a script starts as its page loads, before the browser has answered keploy's question for the page's registrations; one in a page that began while another page of its origin was registering a Service Worker (keploy's Web Lock, above); one in a page that cannot read its Service Workers or its Web Locks (a sandboxed one). keploy marks a Shared Worker only once it knows, as a Service Worker that saw the mark would serve the app a URL other than the one it asked for. The line names the one remedy: with `serviceWorkers: 'block'`, keploy knows at once that no Service Worker can answer, and seeds these.
  - In Firefox, a Shared Worker: Firefox's route does not reach its script. Next step: record and replay the test in Chromium or WebKit to seed it.
  - In Chromium and Firefox, a worker that a worker starts: their routes reach no script of such a worker. Next step: record and replay the test in WebKit to seed it.
  - A worker started from a `blob:` or `data:` URL, or from a URL the browser refuses with keploy's mark (a Trusted Types policy). Next step: start it from its script's http(s) URL.
  - A worker whose script a route of the test's own answered itself (`route.fulfill`). Next step: have that route call `route.continue()` or `route.fallback()` for the worker's script.
  - A Shared Worker whose script a route of the test's own sent on with a URL, method, headers or post data of its own (`route.continue` or `route.fallback` with options), in Chromium and WebKit: the seeding's load of the app's script, which these engines do not route, could not carry them. Next step: have that route continue or fall back with no options for the Shared Worker's script.
  - In Firefox and WebKit, a worker whose script the server redirects (a 301, 302, 303, 307 or 308 answer with a `Location`), classic or module, a Web Worker, and in WebKit a Shared Worker too (Firefox's route never reaches a Shared Worker's script, so a redirected one there gets the Shared Worker line above): Playwright's routes reach only a redirect's first request, so keploy cannot put its seeding ahead of the script at the URL the redirect gives. keploy follows no redirect itself: the worker runs at the URL the redirect gives, as with seeding off (its `location`, `import.meta.url` and the URLs its imports resolve against are the same), with no mark. In Firefox, keploy's answer is the server's redirect, with its `Location` resolved against the URL keploy asked the server for (the app's, or one a route of the test's gave with `continue` or `fallback`). WebKit follows no redirect a route answers with (it refuses one), so keploy sends the request on to the server as the test's routes asked for it, and the server is asked for the script's first URL twice: once by keploy, to see the redirect, and once by the browser. The line says so. Next step: serve the worker's script where the tests run at the URL the app starts the worker at, with no redirect, to seed it. In Chromium such a worker does not start (below).
  - In WebKit, a worker that a Shared Worker starts draws the browser's own numbers too, as WebKit's route reaches nothing a Shared Worker asks for after its script, but no line names it yet (in Firefox the Shared Worker's own line names it).
- **... in Chromium, the server redirects a seeded worker's script.** The worker does not start, where with seeding off it runs at the URL the redirect gives. Chromium never ends a worker's load of a redirect that a route answers with, and Playwright follows no redirect of a request whose URL a route changed: on each hop it asks for the first URL again, until the browser gives up (a test's own `route.continue({ url })` on a worker's script meets the same, with no keploy). keploy changes the URL of a seeded worker's script load, to take its mark off before the request leaves the browser, so in Chromium keploy stops that load (`net::ERR_BLOCKED_BY_CLIENT`) after asking the server for the script once, to see the redirect, and the worker fails to load (its `error` event). This holds for classic and module Web Workers and for Shared Workers, at record and at replay alike. The test prints `keploy: in <test>, the worker at <address> does not start: the server redirects its script, ...` once for each address, with why and the next step: serve the worker's script where the tests run at the URL the app starts the worker at, with no redirect (keploy then seeds it), turn seeding off for that test (`test.use({ keploySeedRandom: false })`), or run it in Firefox or WebKit.
- **... a replay draws otherwise than its recording.** A seed gives a replay its recording's numbers only while each stream is drawn the same number of times, in the same order. The replay's end prints one line for each stream, document and frame path whose count differs from the recording's (above), naming the test, the two counts and the next step. These move a stream:
  - in the test process, what a worker does once, in whichever test first needs it, when another test needs it first at replay (one test replayed alone, or after keploy set an earlier test aside): a worker fixture registered through `@playwright/test`'s own `test`, or through a test type that `mergeTests` returned, whose `extend` and `use` are Playwright's own (register worker fixtures with this package's `test.extend`, or with `extend` on a test type made from it), and a library that draws `Math.random` the first time it is used inside a test (a pool or a cache it builds on first use: use it once outside the tests). This package keeps two such cases out of the test's stream itself: source maps parsed while a stack trace is prepared, and the setup of worker fixtures registered with its own `test.extend` or `test.use` (above);
  - in the test process, a draw made a varying number of times (a retry loop's jitter): one stream serves all of a test's `Math.random` draws, its own and those of the code it calls, Playwright's multipart form boundary among them;
  - in a page, a document whose own draws vary in number before another script draws (a draw per timer tick);
  - frames at one path that the page or a third-party script puts in, in an order or a number that varies run to run (as their scripts load, in network order; a re-render that makes a varying number of frames; chat and support widgets often put in `about:blank` frames as their scripts load): a frame's number at its path is how many frames its parent document had put in at that path before it. Frames under a parent of another origin are counted by their origin in the tab, so two of one origin at one path take their numbers in the order their documents begin. A frame put into a shadow root already in the page is numbered at the document's next numbering (when the app next puts a frame in outside its shadow roots, or when a document of a frame not yet numbered begins), since the parent document watches only the nodes added to or removed from it outside its shadow roots. The line names the frame path whose number of frames differs, and each document whose draws differ; two frames that trade places and draw alike are not named. Next step: give each frame at that path its own `src` path, or put them in in a fixed order and number.
- **... the test process draws outside a test's seed.** The worker's seeded line, once at its first seeded test, names what keeps its own numbers there: the test process's `crypto` (`randomUUID`, `getRandomValues`, `randomBytes`); `Math.random` and faker outside every test (`beforeAll`, `afterAll`, a test file as it loads) and while a worker fixture of this package's `test` is set up, so data made there (a test account made once for the worker's tests) differs each run; and a faker instance the suite makes itself as a test file loads (`new Faker(...)`), for which it names `seedFaker` (above). Where faker is installed but keploy cannot load it, the worker says so once with the reason.
- **... seeding is off.** The first such test of a worker prints what that costs (above).

## What keploy leaves as it is

- The app's server: keploy changes only the test browser and the test process, never the app or its server.
- `crypto.subtle`'s keys in the browser: they stay the browser's own.
- The test process's clock is keploy's run clock, not seeded. A replayed test begins at its recorded begin, or later where the replay is behind, and its clock runs from there. So a value the test makes from the time during the test (`Date.now()`, `new Date()`) is off its recording's by as much as the replay ran faster or slower to that read, while a mocked dependency answers with the recording's: a name stamped with the time in milliseconds differs, and a test that checks it against the dependency's answer fails or is set aside. Give such a value to keploy with `given` (above).
- A context the test makes itself (`browser.newContext()`, `browser.newPage()`), and a `context` fixture the suite overrides without building on this one: keploy does not seed it or wait for its calls, and the test closes it. The end reports only what the `context` fixture's pages drew from, so a test none of whose pages came from it (an API-only test, a context it made itself) says nothing at its end, and keploy keeps what its begin said.

## What seeding adds to a page

- Each document keeps a `MutationObserver` on its nodes (`childList`, its whole subtree) and looks at each node put in (and, while the document holds a numbered frame, each node taken out) for a frame; it walks the document (and its open shadow roots) to number its frames only when the app puts a frame in, or when a document of a frame not yet numbered begins. Most of the cost is the browser's own for such an observer, for each node put in, the parser's included. Measured as the median of five runs: in Chromium, seeding adds about 3 µs a node put in, about 170 ms to the load of a page of 40,000 elements, of which an observer that does nothing takes about 160 ms; in Firefox it adds about 45 ms to that load (27 for that observer), and in WebKit about 40 ms (29). A page that changes 300 times beside 20,000 elements or 2,000 open shadow roots takes within 2 ms of an unseeded one in Chromium and Firefox.
- Seeding keeps a count of each document path of a top document, and of a frame under a parent of another origin, in its origin's session storage in the tab, under the key `__keploy_random_loads`; a frame of its parent's origin is counted by its parent document. The count is kept per origin, so the first documents of one page, or of frames under parents of other origins, at the same path in two origins draw the same numbers. Seeding also keeps two properties on each window, not enumerable: `__keploy_random_page` (the page's name) and `__keploy_random_doc` (what a popup or a frame reads to take its place). In a seeded page, `Math.random`, `crypto.getRandomValues`, `crypto.randomUUID` and `window.open` (which records the popups a document opens) are seeding's own functions, not the browser's native ones: `String(window.open)` shows no `[native code]`.

## Releasing

1. In a pull request, set `"version": "X.Y.Z"` in `playwright/package.json`. The pull request's publish dry run checks the package.
2. Once it is merged, push the tag `playwright-vX.Y.Z` on that commit of `main`: `git tag playwright-vX.Y.Z <sha> && git push origin playwright-vX.Y.Z`. The tag runs the rows, then publishes to npm (`.github/workflows/playwright-publish.yml`).

Push the tag as a plain git tag. Never create a GitHub release for it: a published GitHub release also starts any workflow of this repository that runs on releases, such as the root `@keploy/sdk` release workflow (keploy/typescript-sdk#117), which would try to publish that package under the tag's name and fail.
