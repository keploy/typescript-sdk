# @keploy/playwright

Joins a Playwright suite to keploy's Universal Mocker. `keploy mock record` records the calls each test's browser and app server make; `keploy mock replay` answers them from the recording, so the suite runs without its backends. keploy judges every recorded test, and lists each test it cannot replay with a reason.

This package tells keploy where each test begins and ends. Through it, keploy skips a test it set aside and fails a test whose calls changed. It speaks keploy's scope protocol v1, the same one go-sdk's `keploytest` speaks, and decides nothing itself.

## Use

```sh
npm install --save-dev @keploy/playwright
```

It needs Node.js 20 or later. Its rows run on Node.js 20, 22 and 24.

Import `test` and `expect` from this package instead of `@playwright/test`. A fixture file that extends `test` extends this one:

```ts
import { test, expect } from '@keploy/playwright';

test('lists the apps', async ({ page }) => {
  await page.goto('/apps');
  await expect(page.getByRole('row')).toHaveCount(3);
});
```

Run the suite under keploy with `KEPLOY_PROVEN=1`, one worker and no retries:

```sh
KEPLOY_PROVEN=1 keploy mock record -c "npx playwright test --workers=1 --retries=0"
KEPLOY_PROVEN=1 keploy mock replay -c "npx playwright test --workers=1 --retries=0"
```

`KEPLOY_PROVEN=1` is keploy's switch for its proven model. keploy speaks this package's wire, scope protocol v1 (the claim, begin, end and given), only under it. Without it, keploy answers the worker's claim with a plain 404, and every test of the worker fails with `keploy: this keploy agent answered 404 to POST /agent/instance, so this worker cannot claim keploy's run: ...`, which names the switch.

keploy's first release runs one test process at a time. A second worker that is still alive while another runs is refused by keploy, and its tests fail. Turn retries off: keploy sets aside a test it cannot prove, with its reason, and fails a test whose calls changed, and a retry changes neither.

## Without keploy

With `KEPLOY_MOCK_AGENT` unset or `off`, nothing changes. Only `keploy mock record` and `keploy mock replay` set that variable.

## Under keploy

- **Claim.** Each worker claims keploy's run before its first hook or test (`POST /agent/instance`). The claim uses the worker's Playwright project name as its key, or `.` for an unnamed project, and names the project directory keploy names (`KEPLOY_MOCK_PROJECT`) as the folder of its tests, the folder the test files are named from (the current directory only when keploy names none). So a suite run from a folder above its keploy project, such as `cd .. && npx playwright test` in `mock.command`, is filed under its project. A worker that Playwright starts again after a failed test claims again.
- **Begin.** Each test begins (`POST /agent/scope/begin`) before its `beforeEach` hooks. keploy builds the test's ID as `[project::]file::titles`. The file is relative to the project directory keploy names (`KEPLOY_MOCK_PROJECT`). The titles are the describe groups and the test's own title, joined with ` › `.
- **Skip.** When keploy has set a test aside, the test is skipped through Playwright's own skip, and the report shows keploy's reason (`keploy: ...`).
- **Quiet.** Before the test's `context` (and its `page`) closes, the test waits until its pages have gone 500 ms with no call starting or ending and none in flight. The wait begins when the `context` fixture's teardown begins: after the test's body, its `afterEach` hooks and the teardown of any fixture that uses `page` or `context`. A single-page app keeps making calls after the test's last line has returned: a side panel that loads after an answer, a search made after the test typed. Recorded against a slow backend those calls fall inside the test; replayed, with every answer at once, the test would end before they were made, and keploy would fail it for a recorded call it no longer made. Each call that starts or ends restarts the 500 ms, and time a call is in flight, as the test process sees the calls, counts toward no bound but the 5 s cap below (settle, below, waits for the call by event). So a call a page makes less than 500 ms after an answer, or after the wait began, is the test's at record and at replay alike, however slowly the backend answered at record, within the cap. A call a page's own timer makes while another call is in flight is not: see the limits below. The 500 ms and the 3 s and 5 s below are timers of the test process, and a loaded machine can hold its event loop while the browser's events wait unread. So once one has passed with no call in flight, the wait asks the browser for the context's cookies (answered by the browser itself, not by a page's script, and no step of the report) and ends only after its answer: a call the browser reported before it keeps the wait going, and a call it had not yet reported is not known to the wait. For pages that never go quiet, such as a poller, the wait ends after 3 s with no call in flight, measured with the process's monotonic clock (`performance.now()`), and the test prints `keploy: <test> ended with its pages still making calls: they did not go 500 ms without a call starting or ending in 3000 ms with no call in flight, ...`: a call its pages make later is not the test's, at record or at replay. A call is in flight until the browser reports that its body has loaded; for an answer the page never reads, Chromium reports that about 50 ms after the answer, so the calls of a page that calls every 50 ms or faster without reading the answers overlap, and that page never has time with no call in flight. So the wait is capped: 5 s of wall time from its start, on the same clock, the same at record and at replay. When the cap cuts the wait, the calls in flight then are still waited for to their end (settle, below), and the test prints `keploy: <test>: settle cut at 5 s: calls never went quiet for 500 ms; the page's calls kept it busy ...`. A call a page starts after the cut is not waited for: it falls inside the test only if it reaches the backend before the calls in flight at the cut end, and closing the context cancels it if it is still in flight then.
- **Settle.** A call in flight is waited for until it ends. Calls are counted by the browser's own request events, and no time window decides whether a call is waited for. Once the pages have had a call in flight for 500 ms without a break, the wait for the calls then in flight is a step that names them (`keploy: wait for the test's N call(s) in flight before its browser context closes: ...`). A call still in flight after them is named the same way, in a step of its own. A shorter wait, as the test process sees the calls, is no step, so the report's steps stay the test's; a page whose calls each stay in flight 500 ms or more, such as a poller against a slow backend, shows a step for each. A call that never ends keeps the test waiting, in a step that names it, past the 5 s cap, until Playwright's test timeout fails it. A call is not waited for once the browser has cancelled it, which happens when its page loads another document, its frame is removed, its page closes or the test closes its own context. A closing page cancels only its own calls: a popup that closes cancels nothing of its opener's. A route change inside the page (the history API) cancels nothing, even after an answered call. A service worker's calls are counted too. No page's change drops them, but the test closing its own context does, as it ends the worker.
- **The wait counts toward the test's timeout.** Quiet takes at most 3 s with no call in flight and at most 5 s in all; settle then waits for the calls in flight at the cut to end. A timeout inside a named wait fails that step, which names the calls it waits for. The rest of the wait is no step: the time up to the 5 s cap, and after it up to the 500 ms after which a step names the calls still in flight. A timeout there is reported by Playwright as the teardown of the `context` fixture (`Tearing down "context" exceeded the test timeout of ...`): that teardown is this wait.
- **End.** The test ends (`POST /agent/scope/end`) after its last teardown, with its own outcome. When keploy saw a call with no recorded answer, or a recorded call the test no longer made, the test fails with keploy's text.
- **Given values.** `await given(name, value)` tells keploy a value the test made itself. Examples are a session token it signs and a name it stamps with the time. keploy then follows the value wherever the test's calls carry it, as it follows an incoming request's values in a server test. Give a distinctive value, whole, as the calls carry it. `given` must be called inside a test, or in its `beforeEach` or `afterEach` hooks. It returns the value. It needs a keploy whose agent serves `POST /agent/scope/given` (see the limits below).

- **Seeded random numbers.** Each test's browser draws its random numbers (`Math.random`, `crypto.getRandomValues`, `crypto.randomUUID`) from a seeded stream, so a replay draws the numbers its recording drew. A page that picks what to load at random (an A/B coin, such as stripe.js's at each page load) then makes the same calls in replay as in its recording, which keploy can answer.
  - **Where the seed comes from.** Each test's begin sends a seed drawn afresh (`seed`, 128 bits as hex). keploy answers the seed to draw from. A record answers the begin's own, and keeps it in the test's mapping entry (`seed:`, beside its `at:`). A retry of the test in the same record gets its first attempt's. A replay (and keploy's auto-replay) answers the one the recording kept. So two tests draw different numbers, and recording a test again draws new ones: an ID the browser makes is not sent twice to a real server. The seed is not derived from the test's name, so a test whose entry is renamed keeps its seed with the rest of the entry.
  - **The test process.** The Node worker that runs the test draws `Math.random` from the same seed, from its own stream, from the test's begin to its end: its `beforeEach` and `afterEach` hooks and its fixtures included. So data a suite makes in the test process (a lead named `Lead ${Math.random().toString(36).slice(2, 7)}`) is in replay the data its recording made, and a mocked dependency's answer still matches the test's own assertion. At the test's end the worker's own `Math.random` is back, unless the test put its own stub there, which it keeps.
    - A draw made while a stack trace is prepared is the worker's own, not the test's. Playwright maps stack frames through source maps, and the first time a test's stack reaches a file (a helper or page-object file's `test.step`, an `expect`, a read of an Error's stack), it parses that file's map with a sort that draws `Math.random`. A worker parses each file once, in whichever test reaches it first. So those draws do not depend on which tests its worker ran before it.
    - To tell those draws apart, every stack trace is prepared through a wrapper while a test is seeded: `Error.prepareStackTrace` reads back a wrapper of the function last set there (the same one on each read), and setting that wrapper sets its function. At the test's end `Error.prepareStackTrace` is again a plain property holding the function last set, unless the test defined that property itself, which it keeps.
    - A worker fixture registered with this package's `test.extend` or `test.use` draws the worker's own `Math.random` while it is set up, until it calls `use()` (or fails before). Playwright sets a worker fixture up in the first test that asks for it, after that test's seeding began, unless it is `auto`. Its draws (a test account made once for the worker's tests) would otherwise come from that test's stream and shift the test's own. A test fixture is the test's, and draws from its stream. Anything else that draws while a worker fixture is set up (a timer or an event handler of the test's) draws the worker's own too.
    - With both, a test draws the same numbers whichever tests its worker ran before it: replayed alone, after keploy set an earlier test aside, or in a new worker after a test failed. The limits below name what a worker does once, in whichever test first needs it, that neither covers.
  - **A recording that kept no seed** (made before keploy kept seeds, or with seeding off), a test pulled from a Keploy branch (the branch keeps no seed yet), or a keploy from before seeds, answers none. That test's browser and test process then draw their own numbers, and the test prints `keploy: keploy answered the begin of <test> with no seed, so its browser and its test process draw their own random numbers: ...`. A recording made before seeds or with seeding off is seeded by recording it again with seeding on.
  - **What is seeded.** The seed is installed before any script of the page runs, in every frame of the test's `context`, cross-site frames included. Each function has its own stream, and each document its own. A document is named by its page, by its path (not its host, port or query, which a replay may change), and by how many documents of that path its origin loaded in the tab before. So a reload draws new numbers, the same ones each run, and two tabs of one test at one path draw different ones: an ID the browser makes for each tab (a tab or client ID, an idempotency key) stays its own, in the record as in the app. Only the test browser's pages and the test process's `Math.random` change: not the app, its server or the browser's workers. The first test a worker seeds prints one line saying so, and how to turn it off.
  - **How a page is named.** By its place in the test's own order, the same in every run:
    - a page the test opens (`context.newPage()`, the `page` fixture's among them), by the order in which the test asked for its pages, even when it asks for two at once;
    - a popup a page opens with `window.open`, at the opener's origin, as the window that the opener's document opened first, second, and so on (two popups opened at one moment keep their places);
    - a frame, by the page it is in.

    A document the seeding cannot place draws the browser's own numbers, never another page's. The test then prints `keploy: in <test>, the document at <address> drew the browser's own random numbers, so its draws may differ at replay: ...`, once for each address, in its record and in each replay. The limits below list those documents.
  - **What keploy is told.** The begin says what the test means to do (`random: "seeded"` or `"own"`). The end says what its pages drew from: `"seeded"` when a page opened in its seeded `context`, `"own"` when a page opened there unseeded, or when keploy answered no seed. When a test's calls still vary between runs, keploy can then say whether its pages were seeded, so the variation comes from somewhere the seeding does not reach, or whether seeding them is left to try.
  - **On by default.** To turn it off, for record and replay alike:
    - for the whole run: `KEPLOY_SEED_RANDOM=off` (or `0`, `false`; unset, `on`, `1` or `true` seed; any other value fails every test, naming the variable);
    - for a project, a file or a test: the option `keploySeedRandom: false`, in the config's or a project's `use`, or with `test.use({ keploySeedRandom: false })`. Its type is `KeployOptions`: `defineConfig<KeployOptions>({ use: { keploySeedRandom: false } })`.

    The cost, which the first such test of a worker prints: the test process and the browser draw their own numbers each run, so data a test makes from them differs from its recording's while a mocked dependency answers with the recording's. A test that checks one against the other fails, or keploy sets it aside, and a page's random choice may make calls the recording never saw.

Any answer from the agent that this package cannot trust fails the test. That covers an agent it cannot reach, an error answer, an unreadable answer, and an answer that does not speak scope protocol v1. Nothing is retried.

## Limits of this version

- Quiet and settle cover the `context` and `page` fixtures. A context the test makes with `browser.newContext()` is the test's own to close.
- Quiet waits 500 ms of no call starting or ending. A call a page makes once its pages have gone 500 ms with no call starting or ending and none in flight (a timer of a second or more after the test's last call) is made after the test has ended, so it is not the test's.
- The window is not the same at record and at replay for a call a page's own timer makes while another call is in flight. At record a slow answer keeps the wait going until the timer fires, so the call is the test's. At replay every answer comes at once, the window ends first, and the call is never made, so keploy fails the replay for a recorded call it no longer made. For example, a page that calls `/first` as it loads and `/late` from its own 2 s timer: with `/first` answered after 3 s at record, `/late` is the test's there, and at replay it is not made.
- A page that never goes 500 ms without a call (polling faster than that) waits until 3 s with no call in flight have passed, or until the 5 s cap, whichever comes first. A call is in flight until the browser reports that its body has loaded, about 50 ms after the answer in Chromium when the page never reads it. So a page that calls every 50 ms and reads the answers ends at the 3 s bound while its calls stay short; on a loaded machine they take longer and overlap more, and its wait can end at the cap instead. One that does not read them always has a call in flight and ends at the cap, as does one that calls every 100 ms without reading them, its test taking 5.5 to 5.7 s as measured. A poller that waits G ms after each answer, against a backend that answers after A ms, would take about 3 s x (1 + A / G), with a step for each answer that takes 500 ms or more: against a slow backend at record it ends at the cap, once the call in flight then is answered, while its replay, answered at once, ends at the bound, so the calls it makes between the two are made at replay and not at record. A page that has a call in flight that never ends (a long poll, a stream that never ends) keeps its test waiting past the cap until its timeout, which names the call. Under keploy every test that uses the `context` or `page` fixture takes at least 500 ms longer.
- The cap counts the time calls are in flight, so it is the same at record and at replay only for pages whose calls are answered as quickly at both. A page whose calls keep the wait going for 5 s at record, against a slow backend, and not at replay, leaves different calls to its test at the two: a side panel's call made after an answer that took 5 s at record is not the test's there, and is at replay.
- Quiet knows only the calls the browser has reported. A page whose scripts do not run for 500 ms with no call in flight has gone quiet by that rule, even when only a starved machine held them: the wait ends, and a call the page makes after that is not the test's.
- Settle's rows run in Chromium. Which calls the browser itself ends (a removed frame's) is proven there only; Firefox and WebKit are not rowed.
- Seeding covers the pages of the `context` and `page` fixtures. These draws keep the browser's own random numbers, or the app's:
  - the app's server;
  - in the test process: `crypto` (`randomUUID`, `getRandomValues`, `randomBytes`), and `Math.random` outside every test (`beforeAll`, `afterAll`, a test file as it loads) and while a worker fixture of this package's `test` is set up, so data made there differs each run:
    - a library that seeds itself from them as it loads: `@faker-js/faker`'s default instance seeds its generator from `Math.random` as its module loads, so every value it makes differs from its recording's;
    - data a suite makes once in `beforeAll` or a worker fixture (a test account made once for the worker's tests);
  - Web Workers, Shared Workers and Service Workers, since an init script does not reach them;
  - a context the test makes itself (`browser.newContext()`, `browser.newPage()`), and a `context` fixture the suite overrides without building on this one;
  - `crypto.subtle`'s keys.

  A page whose own draws vary in number before another script draws (a draw per timer tick) still shifts that function's stream within the document.

  In the test process, what a worker does once, in whichever test first needs it, draws from that test's stream and shifts the test's later draws, so a replay where another test is the first to need it (one test alone, or after keploy set an earlier test aside) draws other numbers than the recording. This package keeps two such cases out of the test's stream: source maps parsed while a stack trace is prepared, and the setup of worker fixtures registered with its own `test.extend` or `test.use`. These it does not:
    - a worker fixture registered through `@playwright/test`'s own `test`, or through a test type that `mergeTests` returned, whose `extend` and `use` are Playwright's own. The usual case is fixtures built on `@playwright/test` and joined to this package's `test` with `mergeTests`. Register worker fixtures with this package's `test.extend`, or with `extend` on a test type made from it that way;
    - a library that draws `Math.random` the first time it is used, inside a test (a pool or a cache it builds on first use).

  In the test process one stream serves all of a test's `Math.random` draws, its own and those of the code it calls (Playwright's multipart form boundary among them), so a draw made a varying number of times (a retry loop's jitter) shifts the draws after it.
- The test process's clock is not seeded: it is keploy's run clock. A replayed test begins at its recorded begin, or later where the replay is behind, and its clock runs from there. So a value the test makes from the time during the test (`Date.now()`, `new Date()`) is off its recording's by as much as the replay ran faster or slower to that read, while a mocked dependency answers with the recording's: a name stamped with the time in milliseconds differs, and a test that checks it against the dependency's answer fails or is set aside.
- Seeding cannot place these documents, so they draw the browser's own numbers and are named (above):
  - a popup opened with noopener, as a link with `target="_blank"` opens one, or opened other than by `window.open` (a form, or a link with `rel="opener"`, that targets a new window);
  - a popup at another origin than its opener's page, or whose opener's page has loaded another document by the time the popup's begins;
  - a frame of another origin inside one of those popups.

  The end still says `"seeded"` for such a test: its `context` was seeded. A context init script of the test's own that draws random numbers as a document begins runs before the page is named, so that document has no place either.
- The end reports only what the `context` fixture's pages drew from. A test none of whose pages came from it (an API-only test, a context it made itself) says nothing at its end, so keploy keeps what its begin said.
- Seeding keeps a count of each document path in the page's session storage, under the key `__keploy_random_loads`. A sandboxed frame or an opaque origin has no session storage, so each of its documents at a path in one page draws the same numbers. Two frames of different origins at the same path in one page draw the same numbers. Seeding also keeps two properties on each window, not enumerable: `__keploy_random_page` (the page's name) and `__keploy_random_doc` (what a popup or a frame reads to take its place).
- Calls that `beforeAll`/`afterAll` hooks and worker fixtures make outside every test are answered from the worker's claim, one slice per Playwright project.
- The `beforeAll` and `afterAll` hooks of a describe group whose tests keploy has all set aside still run, and their calls are answered from the claim. Each test is skipped at its begin, after the group's hooks have started; skipping the whole group before its hooks run needs a way to ask keploy for the set-aside tests first, which this version does not have.
- `given` needs the agent route `POST /agent/scope/given` (keploy/keploy#5016). keploy v3.6.192 and later serve it; with the enterprise keploy, that is an enterprise release on keploy v3.6.192 or later. An older keploy answers that route with a plain 404, and `given` fails the test with `keploy: this keploy agent answered 404 to POST /agent/scope/given, so it cannot take the given value <name>: given needs keploy v3.6.192 or later (keploy/keploy#5016), or an enterprise release on keploy v3.6.192 or later; an older keploy answers 404 there`. Claim, begin, settle and end do not need that route.
- Seeds need a keploy that keeps them: keploy vX.Y.Z (keploy/keploy#NNNN) and later; with the enterprise keploy, an enterprise release on keploy vX.Y.Z or later. **[Placeholder: vX.Y.Z and #NNNN are replaced with the keploy release that keeps seeds before this version is released.]** An older keploy reads no seed from a begin and answers none, so each test's browser and test process draw their own random numbers and print the line that says so (above). Claim, begin, settle and end work with it as before.

## Releasing

1. In a pull request, set `"version": "X.Y.Z"` in `playwright/package.json`. The pull request's publish dry run checks the package.
2. Once it is merged, push the tag `playwright-vX.Y.Z` on that commit of `main`: `git tag playwright-vX.Y.Z <sha> && git push origin playwright-vX.Y.Z`. The tag runs the rows, then publishes to npm (`.github/workflows/playwright-publish.yml`).

Push the tag as a plain git tag. Never create a GitHub release for it: a published GitHub release also starts any workflow of this repository that runs on releases, such as the root `@keploy/sdk` release workflow (keploy/typescript-sdk#117), which would try to publish that package under the tag's name and fail.
