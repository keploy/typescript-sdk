# @keploy/playwright

Joins a Playwright suite to keploy's Universal Mocker. `keploy mock record` records the calls each test's browser and app server make; `keploy mock replay` answers them from the recording, so the suite runs without its backends. keploy judges every recorded test, and lists each test it cannot replay with a reason.

This package tells keploy where each test begins and ends. Through it, keploy skips a test it set aside and fails a test whose calls changed. It speaks keploy's scope protocol v1, the same one go-sdk's `keploytest` speaks, and decides nothing itself.

## Use

```sh
npm install --save-dev @keploy/playwright
```

It needs Node.js 20 or later. Its rows run on Node.js 20, 22 and 24.

Import `test` and `expect` from this package instead of `@playwright/test`. A fixture file that extends `test` extends this one:

```ts
import { test, expect } from '@keploy/playwright';

test('lists the apps', async ({ page }) => {
  await page.goto('/apps');
  await expect(page.getByRole('row')).toHaveCount(3);
});
```

Run the suite under keploy with `KEPLOY_PROVEN=1`, one worker and no retries:

```sh
KEPLOY_PROVEN=1 keploy mock record -c "npx playwright test --workers=1 --retries=0"
KEPLOY_PROVEN=1 keploy mock replay -c "npx playwright test --workers=1 --retries=0"
```

`KEPLOY_PROVEN=1` is keploy's switch for its proven model. keploy speaks this package's wire, scope protocol v1 (the claim, begin, end, given and refusal), only under it. Without it, keploy answers the worker's claim with a plain 404, and every test of the worker fails with `keploy: this keploy agent answered 404 to POST /agent/instance, so this worker cannot claim keploy's run: ...`, which names the switch. A begin, an end or a refusal answered with a plain 404 names the switch the same way.

keploy's first release runs one test process at a time. A second worker that is still alive while another runs is refused by keploy, and its tests fail. Turn retries off: keploy sets aside a test it cannot prove, with its reason, and fails a test whose calls changed, and a retry changes neither. keploy runs each test once in a run, so a test Playwright runs again (a retry, from `--retries`, the config or `test.describe.configure`, or a repeat of `--repeat-each`) fails without beginning, saying why, and keploy is told (`POST /agent/refusal`), so its verdict on the run names the test.

## Without keploy

With `KEPLOY_MOCK_AGENT` unset or `off`, nothing changes. Only `keploy mock record` and `keploy mock replay` set that variable.

## Under keploy

- **Claim.** Each worker claims keploy's run before its first hook or test (`POST /agent/instance`). The claim uses the worker's Playwright project name as its key, or `.` for an unnamed project, and names the project directory keploy names (`KEPLOY_MOCK_PROJECT`) as the folder of its tests, the folder the test files are named from (the current directory only when keploy names none). So a suite run from a folder above its keploy project, such as `cd .. && npx playwright test` in `mock.command`, is filed under its project. A worker that Playwright starts again after a failed test claims again.
- **Begin.** Each test begins (`POST /agent/scope/begin`) before its `beforeEach` hooks. keploy builds the test's ID as `[project::]file::titles`. The file is relative to the project directory keploy names (`KEPLOY_MOCK_PROJECT`). The titles are the describe groups and the test's own title, joined with ` › `.
- **Skip.** When keploy has set a test aside, the test is skipped through Playwright's own skip, and the report shows keploy's reason (`keploy: ...`). The test's output shows it too (`keploy: ... (keploy skipped <titles>)`), since Playwright's list, line and dot reporters print a test's output but not its skip's reason.
- **Settle.** Before the test's `context` (and its `page`) closes, the test waits until none of its pages' calls is in flight. Calls are counted by the browser's own request events, and no time window decides. A call that never ends keeps the test waiting until Playwright's test timeout fails it. The test shows a step that names each call still in flight. A call is not waited for once the browser has cancelled it, which happens when its page loads another document, its frame is removed, its page closes or the test closes its own context. Nor are the calls a page's frames had in flight when the page loaded another document: the frames go with the old document, and Playwright reports no end for their calls, ordinary or keepalive (`navigator.sendBeacon`, `fetch` with `keepalive`, the telemetry a payment form's frame sends, which the browser goes on sending), nor for a frame's own document request still loading, so waiting for them would hold the test until its timeout. The browser goes on sending a keepalive call only while the test's context lives: one still in flight when the test ends is cut by the context close, so its answer may not be recorded. A closing page cancels only its own calls: a popup that closes cancels nothing of its opener's. A route change inside the page (the history API) cancels nothing, even after an answered call. A service worker's calls are counted too. No page's change drops them, but the test closing its own context does, as it ends the worker.
- **End.** The test ends (`POST /agent/scope/end`) after its last teardown, with its own outcome. When keploy saw a call with no recorded answer, or a recorded call the test no longer made, the test fails with keploy's text.
- **Given values.** `await given(name, value)` tells keploy a value the test made itself. Examples are a session token it signs and a name it stamps with the time. keploy then follows the value wherever the test's calls carry it, as it follows an incoming request's values in a server test. Give a distinctive value, whole, as the calls carry it. `given` must be called inside a test, or in its `beforeEach` or `afterEach` hooks. It returns the value. It needs a keploy whose agent serves `POST /agent/scope/given` (see the limits below).

- **Seeded random numbers.** Each test's browser draws its random numbers (`Math.random`, `crypto.getRandomValues`, `crypto.randomUUID`) from a seeded stream, so a replay draws the numbers its recording drew. A page that picks what to load at random (an A/B coin, such as stripe.js's at each page load) then makes the same calls in replay as in its recording, which keploy can answer.
  - **Where the seed comes from.** Each test's begin sends a seed drawn afresh (`seed`, 128 bits as hex). keploy answers the seed to draw from. A record answers the begin's own, and keeps it in the test's mapping entry (`seed:`, beside its `at:`). A replay (and keploy's auto-replay) answers the one the recording kept. So two tests draw different numbers, and recording a test again draws new ones: an ID the browser makes is not sent twice to a real server. The seed is not derived from the test's name, so a test whose entry is renamed keeps its seed with the rest of the entry.
  - **A recording that kept no seed** (made before keploy kept seeds, or with seeding off), a test pulled from a Keploy branch (the branch keeps no seed), or a keploy from before seeds, answers none. That test's browser then draws its own numbers, and the test prints `keploy: keploy answered the begin of <test> with no seed, so its browser draws its own random numbers: ...`. A recording made before seeds or with seeding off is seeded by recording it again with seeding on.
  - **What is seeded.** The seed is installed before any script of the page runs, in every frame of the test's `context`, cross-site frames included. Each function has its own stream, and each document its own. A document is named by its page, by its path (not its host, port or query, which a replay may change), and by how many documents of that path loaded before it: in its frame, for a frame of its parent document's origin; else in its origin in the tab. So a reload draws new numbers, the same ones each run, and two tabs of one test at one path draw different ones: an ID the browser makes for each tab (a tab or client ID, an idempotency key) stays its own, in the record as in the app. Only the test browser's pages change: not the app, its server or the browser's workers. The first test a worker seeds prints one line saying so, and how to turn it off.
  - **How a page is named.** By its place in the test's own order, the same in every run:
    - a page the test opens (`context.newPage()`, the `page` fixture's among them), by the order in which the test asked for its pages, even when it asks for two at once, in each of its documents: its first one (the `about:blank` it has before its first `goto`, which `page.setContent` writes into) too;
    - a popup a page opens with `window.open`, at the opener's origin, as the window that the opener's document opened first, second, and so on (two popups opened at one moment keep their places);
    - a frame of its parent document's origin, by that document and by its place among the document's frames: the path its element asks for (`src`, or `about:srcdoc`, or `about:blank` for none) and how many frames the document had put in at that path before it, counted in the order the document holds the frame elements when it numbers them (as the task that put them in ends, or as a frame's document begins), never by their windows (the document finds a frame by its `frameElement`). For frames one task puts in out of document order, that is document order in Chromium and WebKit and the order they were put in in Firefox: the same each run, for a given app and engine. Frames at other paths, and the order the frames' documents load in, do not move it; it keeps its place whatever it loads, and one put in after a frame's removal takes the next number at its path. A frame in an open shadow root is placed so too. An `about:blank` frame does not draw its parent document's numbers;
    - a frame under a parent of another origin, which it cannot read (a cross-site frame), by the page it is in and its path. One with no session storage to count its documents in (a sandboxed frame without `allow-same-origin`) is never seeded (below).

    A document the seeding cannot place draws the browser's own numbers, never another page's. The test then prints `keploy: in <test>, the document at <address> drew the browser's own random numbers, so its draws may differ at replay: ...` with the reason, once for each address and reason, in its record and in each replay. The address is the document's origin and path; for an opaque origin (`about:blank`, `about:srcdoc`, a `data:` URL, a sandboxed frame or page) it is the document's URL with no query or fragment, and `about:blank` for a window's first document that has no URL yet (Firefox runs init scripts there before it has one). The limits below list those documents.
  - **What keploy is told.** The begin says what the test means to do (`random: "seeded"` or `"own"`). The end says what its pages drew from: `"seeded"` when a page opened in its seeded `context`, `"own"` when a page opened there unseeded, or when keploy answered no seed. When a test's calls still vary between runs, keploy can then say whether its pages were seeded, so the variation comes from somewhere the seeding does not reach, or whether seeding them is left to try.
  - **On by default.** To turn it off, for record and replay alike:
    - for the whole run: `KEPLOY_SEED_RANDOM=off` (or `0`, `false`; unset, `on`, `1` or `true` seed; any other value fails every test, naming the variable);
    - for a project, a file or a test: the option `keploySeedRandom: false`, in the config's or a project's `use`, or with `test.use({ keploySeedRandom: false })`. Its type is `KeployOptions`: `defineConfig<KeployOptions>({ use: { keploySeedRandom: false } })`.

Any answer from the agent that this package cannot trust fails the test. That covers an agent it cannot reach, an error answer, an unreadable answer, and an answer that does not speak scope protocol v1. Nothing is retried.

## Limits of this version

- Settle covers the `context` and `page` fixtures. A context the test makes with `browser.newContext()` is the test's own to close.
- Settle's rows run in Chromium. Which calls the browser itself ends (a removed frame's) is proven there only; Firefox and WebKit are not rowed.
- Seeding's rows run in Chromium. Its rows for frames, for a popup that a page's first document opens, for top documents with no session storage, and for the test's own context init script run in Firefox and WebKit too. A popup that a page's first document opens with `window.open('about:blank')` draws the browser's own numbers and is named in every engine: in Chromium it has no session storage (its opener's origin is opaque), and in Firefox and WebKit it has no place, since its document begins before `window.open` returns.
- Seeding covers the pages of the `context` and `page` fixtures. These draws keep the browser's own random numbers, or the app's:
  - the app's server, and the test's own code in Node;
  - Web Workers, Shared Workers and Service Workers, since an init script does not reach them;
  - a context the test makes itself (`browser.newContext()`, `browser.newPage()`), and a `context` fixture the suite overrides without building on this one;
  - `crypto.subtle`'s keys.

  A page whose own draws vary in number before another script draws (a draw per timer tick) still shifts that function's stream within the document.

  Two frames at one path can still trade numbers, unnamed, where the order they are counted in is not the same each run:
  - a frame's number at its path is how many frames its parent document had put in at that path before it, so frames at one path that the page or a third-party script puts in, in an order or a number that varies run to run (as their scripts load, in network order; a re-render that makes a varying number of frames), trade numbers, unnamed. Chat and support widgets often put in `about:blank` frames as their scripts load;
  - frames under a parent of another origin are counted by their origin in the tab, so two of one origin at one path take their numbers in the order their documents begin, which may change at replay;
  - a frame put into a shadow root already in the page is not seen as it is put in, since the parent document watches only the nodes added to or removed from it outside its shadow roots: the frame is numbered at the document's next numbering (when the app next puts a frame in outside its shadow roots, or when a document of a frame not yet numbered, its own included, begins), so one put there before another frame at its path, at a moment that varies run to run, may take that frame's number.
- Seeding cannot place these documents, so they draw the browser's own numbers and are named (above):
  - a popup opened with noopener, as a link with `target="_blank"` opens one, or opened other than by `window.open` (a form, or a link with `rel="opener"`, that targets a new window);
  - a popup at another origin than its opener's page, or whose opener's page has loaded another document by the time the popup's begins, or whose opener the seeding could not place (below);
  - a frame of another origin inside one of those popups;
  - a frame its parent document cannot list (one in a closed shadow root, or in an `object` or `embed` element), one whose document began after the frame was removed, and a frame inside one;
  - a frame under a parent of another origin that has no session storage to count its documents in (a sandboxed frame without `allow-same-origin`), alone under its parent or not, and a frame inside one: nothing tells its documents apart from the next ones at its path there (a reload, or a frame the app puts in again at its place) or from those of a frame beside it, so seeded, they could draw the same numbers. Its line says how many other frames its parent holds, counted once the parent's parser has ended (its `DOMContentLoaded`), so frames its markup puts in after a script that holds the parser count even when this frame drew, and loaded, before they came; when the parser has not ended by the test's end, counted then; when the frame is gone by then (its parent moved on to another document), the line names no other frame;
  - a top document with no session storage that seeding can keep its count in, and a frame of its origin inside one. A document of an opaque origin has none: an `about:blank` loaded after its page's first document, a `data:` URL, a page served with a CSP `sandbox` without `allow-same-origin`, or a popup that a page's first document opens; nor has a document whose app has filled its session storage. Nothing tells such a document apart from the next one at its path in the tab (a reload, or another visit to that path), so seeded, they could draw the same numbers. So a test that loads `about:blank` (`page.goto('about:blank')`) and writes its page into it with `page.setContent` draws the browser's own numbers there: write into the page's first document (before its first `goto`), or serve the page from the app's origin, to seed it. A page's first document has no session storage in any engine either, but it is seeded: it is the one document of its kind in its tab (no later document there is marked, so the rule above holds for each of them), and before `newPage` returns the fixture marks it as the page's first with a value drawn afresh for each context and given only to that context's init script, so a page's own script cannot mark another document so. A frame of another origin inside such a document is placed as any frame under a parent of another origin (above).

  The end still says `"seeded"` for such a test: its `context` was seeded. A context init script of the test's own that draws random numbers as a document begins runs before the page is named, so that document has no place either; its line says it is in a page the test opened.
- Seeding's cost in a page: each document keeps a `MutationObserver` on its nodes (`childList`, its whole subtree) and looks at each node put in (and, while the document holds a numbered frame, each node taken out) for a frame; it walks the document (and its open shadow roots) to number its frames only when the app puts a frame in, or when a document of a frame not yet numbered begins. Most of the cost is the browser's own for such an observer, for each node put in, the parser's included. Measured as the median of five runs: in Chromium, seeding adds about 3 µs a node put in, about 170 ms to the load of a page of 40,000 elements, of which an observer that does nothing takes about 160 ms; in Firefox it adds about 45 ms to that load (27 for that observer), and in WebKit about 40 ms (29). A page that changes 300 times beside 20,000 elements or 2,000 open shadow roots takes within 2 ms of an unseeded one in Chromium and Firefox.
- The end reports only what the `context` fixture's pages drew from. A test none of whose pages came from it (an API-only test, a context it made itself) says nothing at its end, so keploy keeps what its begin said.
- Seeding keeps a count of each document path of a top document, and of a frame under a parent of another origin, in its origin's session storage in the tab, under the key `__keploy_random_loads`; a frame of its parent's origin is counted by its parent document. A frame under a parent of another origin with no session storage (a sandboxed frame) is never seeded (above). A top document with no session storage (an opaque origin) is never seeded either, but for a page's first document (above). The count is kept per origin, so the first documents of one page, or of frames under parents of other origins, at the same path in two origins draw the same numbers. Seeding also keeps two properties on each window, not enumerable: `__keploy_random_page` (the page's name) and `__keploy_random_doc` (what a popup or a frame reads to take its place). In a seeded page, `Math.random`, `crypto.getRandomValues`, `crypto.randomUUID` and `window.open` (which records the popups a document opens) are seeding's own functions, not the browser's native ones: `String(window.open)` shows no `[native code]`.
- Calls that `beforeAll`/`afterAll` hooks and worker fixtures make outside every test are answered from the worker's claim, one slice per Playwright project.
- The `beforeAll` and `afterAll` hooks of a describe group whose tests keploy has all set aside still run, and their calls are answered from the claim. Each test is skipped at its begin, after the group's hooks have started; skipping the whole group before its hooks run needs a way to ask keploy for the set-aside tests first, which this version does not have.
- `given` needs the agent route `POST /agent/scope/given` (keploy/keploy#5016). keploy v3.6.192 and later serve it; with the enterprise keploy, that is an enterprise release on keploy v3.6.192 or later. An older keploy answers that route with a plain 404, and `given` fails the test with `keploy: this keploy agent answered 404 to POST /agent/scope/given, so it cannot take the given value <name>: given needs keploy v3.6.192 or later (keploy/keploy#5016), or an enterprise release on keploy v3.6.192 or later; an older keploy answers 404 there`. Claim, begin, settle and end do not need that route.
- Seeds need a keploy that keeps them: keploy v3.6.217 (keploy/keploy#5121) and later; with the enterprise keploy, an enterprise release on keploy v3.6.217 or later. An older keploy reads no seed from a begin and answers none, so each test's browser draws its own random numbers and prints the line that says so (above). Claim, begin, settle and end work with it as before.

## Releasing

1. In a pull request, set `"version": "X.Y.Z"` in `playwright/package.json`. The pull request's publish dry run checks the package.
2. Once it is merged, push the tag `playwright-vX.Y.Z` on that commit of `main`: `git tag playwright-vX.Y.Z <sha> && git push origin playwright-vX.Y.Z`. The tag runs the rows, then publishes to npm (`.github/workflows/playwright-publish.yml`).

Push the tag as a plain git tag. Never create a GitHub release for it: a published GitHub release also starts any workflow of this repository that runs on releases, such as the root `@keploy/sdk` release workflow (keploy/typescript-sdk#117), which would try to publish that package under the tag's name and fail.
